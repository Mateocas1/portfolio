Comparador de precios de supermercados argentinos

Compara precios de 5 supermercados argentinos (Carrefour, Coto, Disco, Jumbo y Vea): unos 24.500 productos y 47.500 ofertas que se actualizan a diario con USD 0 de infraestructura, emparejados por GTIN-14. Permite armar una canasta entre tiendas, publica las bajas de precio del día. El pipeline de un índice de canasta está armado, pero todavía no produce datos.

Estado: Vercel pausó el sitio hasta el 14/11/2026 por pasar la CPU del plan gratuito. El arreglo ya está integrado y el refresh diario está verde desde el 27/10; la causa y la solución están en el postmortem, más abajo.

Estado: de nuevo en línea desde el 14/11/2026, después de una pausa de 30 días por exceso de CPU en el plan gratuito de Vercel. La causa y el arreglo están en el postmortem, más abajo.

El problema

Comparar precios exige confianza del dato, no solo interfaz.

Un precio comparado solo sirve si el producto es el mismo y el dato está al día: la base del proyecto es un refresh diario con controles de calidad y una identidad de producto por GTIN-14.

Datos 5 supermercados, refresh diario

Carrefour, Coto, Disco, Jumbo y Vea: los datos llegan desde la API de VTEX y la búsqueda de Coto, y cada código (EAN-8, UPC-12, EAN-13) se normaliza a GTIN-14 validando el dígito verificador.

Construcción Next.js, PostgreSQL y Redis

Next.js y TypeScript; APIs REST públicas (búsqueda, productos, historial de precios y lote) servidas desde un snapshot JSON versionado, sin base de datos en el camino de lectura, con rate limiting en Redis y panel de administración con Clerk.

Calidad CI en cada cambio

308 pull requests integrados con GitHub Actions: lint, typecheck, 703 tests, build y Lighthouse. Accesibilidad 1,00 en las 4 URLs medidas y SEO 1,00 en 3 de 4 (/buscar es noindex a propósito).

Operación Refresh programado

Un job de GitHub Actions restaura el estado de PostgreSQL, refresca el catálogo con controles de frescura, publica el snapshot y las bajas de precio del día (página, feed Atom y Telegram), y descarta las bajas sospechosas antes de publicarlas.

Postmortem · octubre 2026

El sitio se quedó sin CPU. El problema era el algoritmo.

El 15/10 Vercel pausó el proyecto por pasar las 4 horas de CPU mensuales del plan gratuito. El plan gratuito no da métricas por ruta, así que lo diagnostiqué leyendo el build y el código y midiendo una réplica local con el snapshot real.

Descarté pagar el plan Pro (hubiera escondido el problema), migrar a Cloudflare Workers (10 ms de CPU por request no alcanzan ni para parsear el snapshot) e ISR (excede la cuota de escrituras).

Causa Productos × ofertas en cada request

Cada producto recorría todas las ofertas: 24.547 × 48.419, unas 1.200 millones de comparaciones y 10-16 s de CPU por request, en el sitemap y las listas, sin caché. Un solo crawler alcanzaba.

Arreglo Índice por EAN y caché en el CDN

Un índice armado una vez por proceso, el sitemap generado en el build, caché del CDN de una hora (nunca para errores ni 429) y robots.txt que deja afuera a los crawlers de IA y a los filtros.

Medición De 10-16 s a 18-173 ms

Las páginas pesadas bajaron de 10-16 s a 18-173 ms de CPU por request; 500 búsquedas de producto, de 4.375 ms a 8 ms. Medido en una réplica local; todavía no está medido en producción: se mide cuando Vercel levante la pausa.

Prueba La misma salida, garantizada por tests

Un oráculo con el algoritmo anterior compara resultados, un Proxy cuenta lecturas para que ninguna ruta vuelva a escalar como productos × ofertas, y 25 casos sobre el snapshot real dieron salidas idénticas.
